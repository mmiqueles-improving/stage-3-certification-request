## Day 2 — Introduce v2, Compare
- [x] `npm run eval` (v1+v2 combined) was already run on Day 1; reviewed the results side-by-side today in `promptfoo view`.
- [x] Observation: the difference between v1 and v2 output is notorious/obvious — driven almost entirely by the structure and detail each prompt template asks for, not just model variance.
- [x] Both v1 and v2 critiques contained suggestions, but only v2's prompt explicitly requires a labeled field for it: `**Fix Suggestion**: [concrete, implementable fix]`. v1 never asks for this, so its suggestions are buried in free-form prose.
- [x] Judgment: v2 is meaningfully better at turning critique into actionable items, because its prompt also requires "Issue," "Severity," and a named "heuristic" per item as a structured list — for design critique, a structured checklist beats one big paragraph.
- [x] Result: all 5 v1 cases failed, all 5 v2 cases passed. This is driven by (a) v1 having no structure/persona at all, and (b) the rubric being simple — see limitation below.
- [ ] **Rubric limitation identified**: of the 4 assertions in `defaultTest.assert`, only 1 (actionability) is actually LLM-graded (`llm-rubric`), and it's binary pass/fail — not a graded scale. This means the rubric can tell us both prompts passed/failed a low bar, but can't distinguish "v2 is clearly better" from "v2 is only marginally better" than v1. Next step: either move to a graded 1–5 `llm-rubric` scale (promptfoo supports a `threshold` on rubric scores) or add more finer-grained rubric assertions.

## Day 3 — Real-world Case + Rubric Split
- [x] Split the single binary "actionability" `llm-rubric` into two named binary sub-criteria: `actionability-specificity` (fixes reference concrete UI states) and `actionability-concreteness` (≥3 implementable, non-generic fixes). Kept both binary (not a 1-5 score), per decision to avoid the local `llama3.2` model's known weakness with numeric/counting judgments (Day 1 finding).
- [x] Added `metric` names to every assertion (`heuristic-coverage`, `structure-issue-marker/severity-marker/fix-marker`, `filler-phrase-check`) so `promptfoo view` now shows a labeled result per criterion instead of one lumped score — this was the main ask for "finer resolution."
- [x] Added a 6th real-world fixture: "Hidden confidence and provenance gap" — a legal research agent producing a contract risk analysis with no inline citations, confidence scores, or source attribution, so the user can't verify claims before relying on it for a legal decision. Complements the existing "Transparent agent reasoning" fixture with a different, higher-stakes domain (legal) and a provenance/verifiability angle rather than just "confidence level."
- [x] Ran `npm run eval` (6 fixtures × 2 prompts = 12 cases) — `eval-2xp-2026-08-12T15:25:36`. Overall pass rate: 1/12 (8.3%), down from Day 1's v2 100%. **This is not a regression in v2's prompt quality** — confirmed by inspecting `namedScores` per test: v2 still passes `structure-*`, `heuristic-coverage`, and `filler-phrase-check` on almost every case. The drop is because pass now requires 2 independent local-model judgments (specificity AND concreteness) instead of 1 combined one, and it only takes one of those two to fail for the whole test to fail.
- [x] **This confirms the finer-resolution goal worked**: e.g. the "Streaming response," "Agent handoff," and legal-research (new) fixtures all show v2 passing `actionability-concreteness` but failing `actionability-specificity` (or vice versa for the handoff case) — a distinction the old single combined rubric couldn't surface.
- [x] **New reliability finding**: inspecting the raw grading output (`/tmp/day3-eval.json` component results) for several failing cases, `llama3.2`'s stated `reason` text sometimes flatly contradicts its own `pass: false` verdict on these narrow binary sub-rubrics — e.g. reason = "the critique provides explicit, actionable recommendations for fixing issues" or "the critique provides at least 3 fix suggestions that are concrete and implementable as stated" while `pass: false, score: 0`. This shows the local model's binary yes/no grading isn't fully reliable either, not just its numeric/counting ability (Day 1's finding).

## Day 3 (continued) — Fixing the grading-reliability issue
Rather than ship the rubric split with a known-unreliable grader, investigated and fixed it same-day:
- [x] **Mitigation 1 — `temperature: 0`** on both providers, verified via `npx promptfoo eval --repeat 2`: 0 inconsistencies across repeats (same input → same verdict every time). This proved the earlier contradictions were *reproducible/systematic*, not random noise — a more serious finding than plain flakiness.
- [x] **Mitigation 2 — stronger rubric prompt**: added "state evidence for/against, then your pass value must follow from that evidence; do not contradict your own reason" to both `actionability-specificity` and `actionability-concreteness`. This raised v2's pass rate from 1/6 → 4/6 fixtures by fixing several contradictions, but 2/12 cases still showed the model's `reason` text affirming the rubric (sometimes verbatim) while `pass: false`.
- [x] **Mitigation 3 — bigger grading model**: pulled `llama3.1:8b` (4.9GB, via `ollama pull llama3.1:8b`) and switched *only* `defaultTest.options.provider` to it, keeping generation on `llama3.2` (2GB) for comparability with Day 1/2. Re-ran with `--repeat 2`: 0 inconsistencies, and manual inspection of `reason` vs `pass` showed no remaining contradictions.
- [x] **Final Day 3 eval** (`eval-cuX-2026-08-12T17:48:25`, single clean run, 6 fixtures × 2 prompts, `--no-cache`): **v1 = 0/6 (0%) pass, v2 = 6/6 (100%) pass.** Per-metric breakdown shows v1 now passes `actionability-specificity`/`actionability-concreteness` in every case (some of its suggestions are genuinely fine) but fails 100% on `structure-*` (it was never told to use the format) — a clean, explainable result, unlike the noisy intermediate runs above.
- [x] Updated `README.md`: Evaluation Rubric section (5 criteria, `metric` names, dual-model setup + why), Prerequisites (now requires `llama3.2` + `llama3.1:8b`), and Quantified Improvement Evidence (Day 3 update with the clean 0%/100% result and a summary of the reliability investigation).

## Day 4 — Stress-test Rubric (Bad vs. Well-designed Flow)
Kept this deliberately minimal (observation only, no prompt/rubric edits today) after discussing scope with the reviewer — decided not to pre-emptively change the v2 prompt before seeing real evidence, to avoid repeating the reactive-fix-chasing pattern from Day 3.
- [x] Added 2 new fixtures to `testcases/fixtures.yaml` (now 8 total): (7) "Compounding failures agent" — a financial-reconciliation agent that auto-submits irreversible transactions with no confirmation, no progress, no cancel, and a blank error screen on partial failure (stacks multiple violations at once, unlike the existing 6 which are each one issue). (8) "Well-designed export flow" — an agent with a live progress bar, cancel button, confirmation before overwrite, detailed error+retry, and an explained/overridable default choice. Deliberately designed to have **no real UX issues**, to stress-test whether the rubric can tell the difference.
- [x] Ran `npm run eval --no-cache` (8 fixtures × 2 prompts = 16 cases) — `eval-CIY-2026-08-13T13:26:24`. Result: 8/16 passed (50%) — same clean pattern as Day 3 (v1 fails all 8 on `structure-*`, v2 passes all 8).
- [x] **Compounding-failures fixture behaved as expected**: v2 correctly identified the irreversible-submission issue as the top item (Severity: High) among others — confirms the rubric/prompt handle a "everything is wrong at once" flow fine, within the 5-issue cap.
- [x] **Well-designed fixture surfaced a real, predicted rubric/prompt gap**: v2 still passed (6/6 criteria) by **fabricating 5 issues** on a flow with no real problems — e.g. it flagged "Inadequate confirmation before destructive actions" even though the fixture explicitly states there's a confirmation dialog before overwriting, and nitpicked cosmetic details (progress bar "more prominent," a dropdown instead of the agent's already-overridable default) dressed up with fabricated severities and heuristic labels. v1 was comparatively more honest (opened with a "Strengths" section acknowledging the good design) but still added some generic, unearned "weaknesses."
- [x] **Root cause**: neither prompt has permission to say "no significant issues found," and the rubric's `actionability-concreteness` requirement (≥3 concrete fixes) plus v2's "List each issue found" instruction structurally forces the model to invent problems on a clean flow — and currently the rubric *rewards* this fabrication with a full pass, since the fabricated fixes are still "concrete" and reference real UI elements from the fixture (just spun negatively).
- [x] **Decision**: did not fix this today (kept Day 4 to observation only, per plan). This is queued as one of Day 5's "1–2 concrete prompt changes" — validated evidence rather than a guess. Candidate fix direction: add an explicit instruction allowing/requiring the critique to state "no significant issues found" when true, and adjust the rubric so a legitimate "no issues" critique isn't penalized by the ≥3-fixes requirement (e.g., make that requirement conditional, or add a distinct assertion for "did not fabricate issues on a sound design").
